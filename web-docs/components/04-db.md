# PostgreSQL 数据层

`packages/db` 是控制面的 PostgreSQL 契约层：它用 Goose migrations 定义持久模型，用 sqlc 生成类型安全查询，并为 core、Dashboard 与 Auth 暴露不同的 client 视图。

> **已同步至 2026.30**。

## 2026.30 变动速览

| 主题 | 一句话 | 详见 |
| --- | --- | --- |
| `access_tokens` 退役 | 表与 `generate_access_token()` 函数一并 `DROP`；auth sqlc 的 `access_token/` 子目录消失 | §1、§3 |
| Auth 读写分离被移除 | `authdb.Client` 不再有 `Read`/`Write` 双 pool，改为单 pool + 内嵌 `*authqueries.Queries` | §4、§5 |
| `project_limits` 新表 | 外部服务推送的**绝对配额**，`team_limits` 视图逐列 `COALESCE` 覆盖 tier+addons | §3 |
| `projection` schema | 两张 revision 账本，拒绝乱序到达的投递；写入方是 dashboard-api 的 management service | §3、§6 |
| 磁盘配额新列 | `tiers.default_free_disk_size_mb` / `max_disk_size_mb` 与 `addons.extra_max_disk_size_mb` | §3 |
| 一批性能维护迁移 | 6 个索引增删、4 张表的 autovacuum scale factor、3 处列级统计目标 | [数据库 Schema 全表参考](../database-schema.md) §9.2 |

## 1. 系统位置

DB 包本身不是数据库服务，也不监听网络；它是多个 Go module 共同 import 的库与 migration 镜像。

```text
packages/api ----------- core queries -----\
packages/dashboard-api - dashboard/core ----> pgx pool -> PostgreSQL
packages/auth ---------- auth queries ------/
                              |
                     Goose migrations + sqlc
```

目录按职责拆分：

- `migrations/`：主 schema 的增量历史（2026.30 为 133 个文件），也是生产 migrator 的输入。
- `queries/`：core 资源查询及生成代码，按 `builds/`、`snapshots/`、`templates/`、`template_aliases/`、`teams/`、`sandboxes/`、`volumes/` 分目录，生成物与查询源共置。
- `pkg/dashboard/sql_queries/`：Dashboard 页面投影查询，分 `clusters/`、`teams/`、`templates/`；另有 `pkg/dashboard/migrations/` 存放 Dashboard 专属迁移。
- `pkg/auth/sql_queries/`：Auth 查询，分 `api_keys/`、`teams/`、`user_identities/`、`users/`、`users_teams/`。⛔ 原 `access_token/` 子目录随表退役在 2026.30 删除。
- `client/`、`pkg/auth/client.go`：连接池和查询集合的装配。
- `pkg/types/`：JSONB、build status 与 paused Sandbox config 等手写类型。
- `schema/`：只给 sqlc 解析用的补充 DDL（如迁移链外的 `billing.sandbox_logs`），不是真实迁移。

## 2. 启动/装配

主 migrator 是 [`packages/db/scripts/migrator.go`](../../../packages/db/scripts/migrator.go)。它用 `_migrations` 作为 Goose tracking table，获取 PostgreSQL session lock，再顺序应用 `packages/db/migrations`。

API 与 Dashboard API 启动时调用 `CheckMigrationVersion`，只接受“当前版本大于或等于构建期 expected migration”；它们不会在应用进程内自动执行 migration。

运行时连接由 `pool.New` 创建：

1. 解析 pgxpool DSN 与 caller options。
2. 安装 OpenTelemetry pgx tracer。
3. 使用 `QueryExecModeExec`，禁用 prepared statement cache。
4. 注册 `uuid[]` codec。
5. 创建 pool 并注册连接池 metrics。
6. 在返回给 sqlc 前套一层 transient-error retry wrapper。

[`packages/db/sqlc.yaml`](../../../packages/db/sqlc.yaml) 定义四次生成：core、Dashboard、Auth 和 testutils。Dashboard 的 sqlc schema 还读取 `pkg/dashboard/migrations`；主 migrator 只读取 `migrations/`，因此运行环境必须用部署流程确保 Dashboard 专属的 `env_defaults` 和 `teams.profile_picture_url` 已存在。

## 3. 核心机制与关键对象

| 对象 | 职责 | 特点 |
| --- | --- | --- |
| `client.Client` | core query facade | embeds `queries.Queries` |
| `client.Client.Dashboard` | Dashboard 专用查询 facade | 与 core 共用一个 pool/transaction |
| `authdb.Client` | Auth query facade | 2026.30 起内嵌 `*authqueries.Queries`，只持有一个 pool |
| `pool.New` | 连接、telemetry、codec 与 retry 装配 | 返回 retry DBTX + raw pool |
| `retry.Wrapper` | 对可重试 pgx 错误执行退避重试 | 默认最多 5 次，带 jitter |
| `queries/*` | sqlc 生成的参数、row 与 method | 不手工编辑 |
| `pkg/types` | sqlc override 使用的领域值 | JSONB、BuildStatus、PausedSandboxConfig |

核心持久模型按关系可这样理解：

```text
public.users --< user_identities
      |
      +--< users_teams >-- teams -- tiers/addons -- project_limits -> team_limits view
      |                         |                    ^
      +--< team_api_keys        +--< envs -> active_envs view
      |                               |--< env_aliases
      |                               |--< env_build_assignments >-- env_builds
      |                               |--< snapshots
      |                               |-- snapshot_templates
      +--< volumes
      +--> clusters

projection.project_members / projection.project_limits   (revision 账本，写到上面两张读侧表)
```

⛔ `public.access_tokens`（及其 `user_id` 入向关系）已在 2026.30 由 `20260823120000_drop_access_tokens.sql` 删除；用户级凭证路径只剩 `team_api_keys`。

`active_template_builds` 是并发 build 配额的显式登记表；它和 `env_builds.status_group` 的索引共同支撑“活跃构建”查询，不应通过扫描全部历史 build 重新推断。

`team_limits` 视图自 2026.30 起逐列 `COALESCE(project_limits.<列>, tiers.<列> + addons 增量)`。⚠️ 反直觉细节：`addons` 的求和仍是 `LEFT JOIN LATERAL` 子查询，但**只在 `project_limits` 侧为 NULL 时才生效**——所以给一个 team 写入 `project_limits` 会整列盖掉原先由 addon 抬高的额度，而不是叠加。

## 4. 主请求或数据流

### 普通查询

```text
handler/service
  -> sqlc method(typed params)
  -> retry DBTX
  -> pgxpool
  -> PostgreSQL
  -> generated Row / domain override type
```

retry 只处理被判定为 transient 的 DB 错误，并遵守 request context；业务约束、not found 和唯一键冲突仍原样返回，由上层映射为 HTTP/gRPC 状态。

### Core + Dashboard 共用事务

```text
db.Client.WithTx(ctx)
  -> pool.BeginTx
  -> core Queries.WithTx(tx)
  -> Dashboard Queries.WithTx(tx)
  -> caller 执行多条写入/锁定
  -> caller 显式 Commit 或 Rollback
```

`WithTx` 不自动提交。调用方通常立即 `defer tx.Rollback`，成功路径再显式 `Commit`。

### Auth 单 pool（2026.30 起）

```text
authdb.NewClient(ctx, databaseURL, options...)
  -> 单个 pgxpool.Pool
  -> Client 内嵌 *authqueries.Queries
  -> Read / Write 两个 facade 与 replica pool 均不存在
```

ⓘ 2026.29 及更早，`NewClient` 接收第二个 `replicaURL` 参数，暴露 `Read`（读副本 pool）与 `Write`（主 pool），由 `AUTH_DB_READ_REPLICA_CONNECTION_STRING` 环境变量驱动；该环境变量与 `AuthDBReadReplicaConnectionString` 配置字段在 2026.30 一并移除（2026.29 定义见 `packages/api/internal/cfg/model.go:85` 与 `packages/dashboard-api/internal/cfg/model.go:21`）。2026.30 只剩 `AUTH_DB_CONNECTION_STRING`（`packages/api/internal/cfg/model.go:107`、`packages/dashboard-api/internal/cfg/model.go:21`）。

因此“所有 SELECT 都走副本、写入走主库”这条一致性边界不再存在：**2026.30 起 auth 读路径不再有副本滞后问题，也不再需要为 read-after-write 特意选 `Write`**。

## 5. 设计不变量与故障边界

- schema 的事实来源是有序 migration，而不是生成的 `models.go` 或文档表格。
- SQL 源文件是查询事实来源；`*.sql.go` 是生成物，修改后会被下一次 `sqlc generate` 覆盖。
- `active_envs` 是 env 读路径的规范入口，用来排除 `deleted_at` 已设置的模板。
- Template 与 Build 是多对多关系，关联和 tag 位于 `env_build_assignments`，不能只依赖 `env_builds.env_id`。
- build 读侧分支应使用 `status_group`；原始 `status` 保存执行协议的细粒度历史值。
- team 限额来自 `team_limits` view，它合并 tier 基础值、有效 addons 与推送来的 `project_limits`，不等同于只读 `tiers`。
- `project_limits` 的覆盖是**整行级**：一行要么覆盖全部九项配额，要么不存在（所有列 `NOT NULL`），不存在“半覆盖”的 team。
- 推送类写入必须让 `projection.*` 的 revision 与目标值落在**同一个事务**里；只推进 revision 而不落值，会让之后每次重试都被判为重复丢弃，目标永久停在旧值。
- API key 表保存 hash 和 mask metadata，不保存可再次读取的明文 secret。⛔ 用户级 `access_tokens` 表已于 2026.30 删除，同类字段不再存在。
- `user_identities` 以 `(oidc_iss, oidc_sub)` 为主键，并外键指向 canonical `public.users`。
- running Sandbox 不在 PostgreSQL 建立主记录；`snapshots` 保存 pause 后的 durable 状态，`billing.sandbox_logs` 保存历史 record。
- Auth 侧 2026.30 起只有单个 pool，不再有 read replica 滞后语义；需要 read-after-write 的路径不再需要区分读/写 facade。
- pool retry 不等于事务重试；事务中出现 serialization/deadlock 后，caller 仍需决定是否重放整个事务。
- migration version check 只检测下限，不验证 schema 中每个对象；专属 migration 缺失仍可能在首个查询时报 undefined table/column。
- Dashboard 专属 migration 与主 migrator 目录分离；`sqlc` 能生成成功不证明部署数据库已应用该对象。

## 6. 与其他组件边界

- 与 `packages/api`：DB 持久化 template/build/snapshot/volume/cluster；Redis 中的 running Sandbox 与路由不属于本包。
- 与 `packages/dashboard-api`：Dashboard 使用 core queries 展示 build/record，使用 `Client.Dashboard` 展示 team/template 投影。
- 与 `packages/auth`：DB 提供 credential、identity、membership 与 team-limit 查询；凭证格式、OIDC 校验和缓存属于 auth。ⓘ `packages/auth` 在 2026.30 整体 `internal/` 化（公开路径仅剩 `pkg/auth/*.go` 与 `pkg/types/`），DB 文档中引用它的旧路径需按 `internal/` 后重新定位。
- 与 `packages/dashboard-api` 的 management service：`packages/dashboard-api/internal/management/` 是 `project_limits` 与 `projection.*` 的**实际写入方**，用两个 client（auth pool 写成员投影、主 pool 写配额），两个事务不跨库。
- 与 ClickHouse：Sandbox metrics 与 team metrics 不在 PostgreSQL schema 中。
- 与 Loki：运行日志不由本包持久化；DB 只保存定位日志所需的资源 metadata。
- 与 migration 部署：应用只验证版本并使用 schema，真正的变更执行属于 migrator/job。
